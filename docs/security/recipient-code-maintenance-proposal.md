## 検討中の境界

以下はいずれも **Proposal** であり、実装方式や新しい Decision として確定していない。

1. 鍵 scope の Actor との束縛、全世代の完全列挙、削除中の新規割当の封鎖を Provider 契約として表現する。DB 行がない場合も、信頼できる inventory と未完了 ticket の最早期限を失わない。
2. 小 Batch の処理が継続的な発行によって進捗不能にならないよう、固定された列挙とその後の変更を漏れなく追跡する。監視できない期限・不完全な列挙・証拠不明を成功にしない。
3. Actor 無効化の確定後に、対象 Actor の全 scope を再確認する必要がある。清掃と Actor 削除が競合するときは Lock を保持したまま別処理を待たず、既存の Prepared / Ledger / Witness と各 ticket の所有・期限を維持する。
4. 結果不明や部分的な鍵破棄では、DB の 0-row のみを完了とみなさず、同一操作の ticket・全世代 closure・DB 不在を再照合する。既知の期限未達は既存の隔離契約に従う。

旧形式の durable inventory が実環境に存在するか、完全列挙できるかは未確認である。未知 scope は無視せず安全側へ停止し、実移行の必要性が確認された場合は #245 と Production Gate との責務を含めて別途判断する。

### 現状コードの事実（評価で追加確認）

- `AuthenticationKeyScope.recordKind`は`AuthenticationRow['recordKind']`（`google-identity`/`login-attempt`/`session`）と同じ型で、Record暗号のDEK Port（`allocateForSeal`/`readKey`/`requestRotation`）とRecord Codecにも使われる。保守専用の型ではない。
- 実行時ガード`authenticationMaintenanceScope`は3種以外を拒否する。コードscopeは「保守に含まれない」のではなく**明示的に拒否される**。これはProvider scope検証での拒否であり、旧保守Reader側の拒否の実体かは未確認である。
- PG清掃の`absent`は`google-identity`/`session`以外を`login_attempt`として照会する暗黙分岐を持つ。清掃Serviceも`google-identity`以外の全scopeをCredentialとして破棄する。型の拡張だけでは誤った表を照会し、Actor削除Workflowを経ずに破棄し得る。
- ticket系`AuthenticationKeyDestructionPort`（scope単位の`destroy(ticket)`）とコード系`RecipientCodeMacKeyLifecyclePort`（`inventory`/`closeAllGenerations`/`verifyClosure`）は別契約で、橋渡しは未定義。既存の清掃Serviceはコード用の再開入口を持たない（`deleteExpired`と`pendingCredentials`だけを走査する）。
- 削除Serviceの`begin`は`google-identity`1件だけを`prepare`する。`prepareAuthenticationDestruction`は`authenticationMaintenanceScope`で検証した期待scope集合との完全一致を要求する。`resume`はLedgerのintentと`targetReference`から`find`し、`pendingActorDeletions`はintent不在時の孤児票検出に使う。
- 既存のPG清掃AdapterはActor行を`FOR SHARE SKIP LOCKED`で読み、`digests.verifyActorState`でMAC検証してから使う。ただしR4はコード清掃が本人Actorを**最初から`FOR UPDATE`**で扱うと定める。`disabled_at_ms`は`0005`に存在し、Actor削除はSession/Identityを除去してもActor行をdisabledのまま残す。
- key-stateの読取は既知集合外のpurposeを`additionalPurposes`なしでは拒否する。既存の保守読取は`additionalPurposes`を持たず、コード用の読取は`quarantined`を許さない。`authenticationRetentionWindow`はattempt/session/auditだけを受理する。`quarantined`から`active`への遷移はRestoreだけが持つ（`quarantined`→`restoring`→`active`）。

### Actor削除の順序・再開・封鎖（Cの前提。ADR追補の二択(i)を仮定した場合）

1. 既存どおり外部LedgerへPrepared（`preparedAt`）をappendする。
2. コード専用Portで対象Actorの新規`allocate`を封鎖する（削除専用。Restore時の扱いは#245）。Providerは**封鎖後に返す列挙snapshotが、封鎖前に受理済みの全`allocate`を含む（linearizable）**ことを保証する。封鎖登録は冪等とする。
3. snapshotの各scopeについてコードticket（1 ticket=1 codeId、起算`preparedAt`）を登録する。
4. 既存どおりActor/Session/Identityを無効化・除去する。
5. 各コードticketでDB行除去→全世代closure→0-rowを確認する。
6. 封鎖後に再snapshotし、全scopeが`byOperation`（所有または採用）の検証済みticketと一致することを確認した場合だけ、外部LedgerへCompleteをappendする。

再開: 削除Serviceは同`operationId`でコードticketを`find`し、Prepared後・コードticket作成前に落ちた場合は封鎖（冪等）と列挙を再実行して不足分を登録する。既存の`resume`はLedgerのintentからActor票だけを引くため、コードticket用の入口（`byOperation`）を追加する（ADR追補の対象）。`allocate`封鎖後は、封鎖Actorのコードに対する鍵rotationの再MACも`unavailable`になる。overdueの`quarantine`は既存どおり認証全体の封鎖であり、コード1件の遅延でも認証全体が止まることを停止契約へ明記する。

### 旧保守Writerの停止契約（記述場所・条件・検証）

- 条件: `authenticationMaintenanceScope`と既存の保守経路は`recipient-code`を拒否し続ける。コード用途は新Portだけが扱う。旧Writerが`quarantine`/overdue封鎖の後に利用受付へ戻らないこと、`key_state`を`active`へ戻さないことを契約とする。確認済みの事実: コードの発行・管理経路は`key_state`が`active`/`rotating`の場合だけ許可し、`quarantined`/`restoring`を拒否する（`authentication-key-state.ts`）。清掃だけが`quarantined`を許す。確認済みの事実: `quarantined`から`active`へ戻す遷移を持つのはRestoreだけである（`quarantined`→`restoring`→`active`、清掃は`quarantined`へ倒すだけ）。A1で、旧Writerがこの遷移を起こせないことと、既知集合外purposeの拒否を実PGのTestで固定する。
- 共存: コードpurposeの初期化は#244の範囲外で、初期化前に既存清掃・削除・4認証APIがコードpurposeなしで従来どおり動作することを回帰で固定する。初期化後は既存の清掃・削除Adapterの読取拡張（推奨案7）を前提とし、通常Storeのreaderは止まったままとする。
- 記述場所: 新Portのdoc comment、認証保守README、Runbook、capability matrix。
- 検証: 「既存保守経路が`recipient-code`scopeを拒否する」Red、および`quarantined`でのコード発行・消費の拒否と、旧Writer共存時に封鎖状態から受付が再開しないTestをA1で固定し、Bで清掃経路へ拡張する。#245のRestore固有の再開禁止は渡す。
